# Brief — ticket #3: Severity-ranked flags, each showing its verified source sentence

This is the ticket the whole product rests on. ADR-0001 is not a quality bar here,
it is a correctness requirement: **a flag whose source sentence cannot be shown is
a bug, and no code path may produce one.**

## What to build

`analyzeDocument(text, redLines, deps)` now returns real `flags[]` beside the
summary. Red lines are **not** used for the override yet (that is #11) — accept
the argument and pass it through.

### The verification step — the heart of this ticket
Every flag the model proposes carries a quoted source sentence. Before a flag can
enter the returned output, that sentence is checked **verbatim** against the input
`text`. A flag that fails is **dropped entirely** — not repaired, not fuzzy-matched,
not included with an approximate quote, not included without one.

Put this in its own module with its own tests. It must be structurally impossible
for a flag to reach the output unverified: make the verified flag a distinct type
the output only accepts, rather than relying on a call in the right order.

Be careful about what "verbatim" means. Exact substring is the rule. You may
normalise whitespace *on both sides symmetrically* if PDF extraction realistically
demands it — but if you do, the sentence stored and displayed must be the one
found **in the document**, never the model's version of it. Record the choice.

### Filtering and ranking
- **Plausibility filter, applied before ranking** (ADR-0004): a clause is
  dangerous when it lets the other side change the reader's economics
  unilaterally after the reader is committed. A non-standard but *symmetric*
  clause (odd governing law, odd notice address) is **dropped entirely, never
  ranked low**.
- **Severity ranks consequence, not frequency** (ADR-0004).
- **Recall over precision** (ADR-0006): a citable clause that passed the
  plausibility filter is flagged even when harm-confidence is only partial.

Flag wording in this slice is plain. Hedging is #5 — do not build it, but leave
the structured output room for the separate ambiguity signal #5 needs.

### Persistence and the screen
- The analysis result is persisted with the document (the store from #2).
- Flags render in severity order, each with its source sentence visible, following
  `DESIGN.md`: the focused flag in crimson #B3122E, every other flag resting in
  grey #E7EAEE, ranks in fixed slots in the change-bar gutter, document text in
  Tinos, no shadows/gradients/pills/badges. Choosing a flag moves the crimson
  focus and scrolls the page to its sentence — the signature interaction in both
  surface briefs.

## Tests (with the stub model client — no live model call, ever)
- **The required correctness test:** feed a stubbed model response containing
  (a) a fabricated source sentence that is nowhere in the fixture text and
  (b) a "tidied up" version of a real sentence (punctuation or casing changed).
  Both flags must be absent from the output entirely. A real, verbatim one in the
  same response must survive. This is the acceptance criterion, stated literally.
- A fixture with a symmetric-but-unusual clause produces no flag for it — use
  `decoys.symmetricUnusual` from the adhesion sidecar.
- A partially-confident but citable dangerous clause still produces a flag — use
  the sidecar flag with `harmConfidence: "partial"`.
- Flags come back ordered by descending severity.
- Remember: with no red lines supplied, the `plausible: false` flag must NOT
  appear (see the shared brief's sidecar section).
