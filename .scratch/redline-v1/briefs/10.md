## What to build
A signed-in reader builds and edits their own list of **red lines** — terms they
decided in advance they won't accept, written in their own plain language. The
list belongs to the reader, persists across sessions and across every document,
and is read by the analysis on each run.

This slice is the list itself. Making red lines actually drive the analysis is
#11 — do not build the override here. What you must do is wire the plumbing: the
analysis entry point receives the reader's current red lines as the `redLines`
argument of `analyzeDocument`, read fresh at analysis time.

A `red_lines` table with Row Level Security so a reader sees and changes only
their own, written as SQL under `supabase/migrations/`. Do not attempt to run it.

Empty state: "no red lines yet" is listed in the app shell brief as a state to
design. It should invite the reader to write one, and it must not imply the
product is broken without them.

## Tests
- Add, edit and delete each work against the store seam (stub the Supabase client
  at the seam; do not mock the store you are testing).
- The list persists across documents — analysing a second document reads the same
  list.
- A reader cannot read or change another reader's red lines. Assert on the policy
  the migration creates as well as the query path.
- `analyzeDocument` receives the reader's current red lines, read at analysis time
  rather than from a stale copy.
