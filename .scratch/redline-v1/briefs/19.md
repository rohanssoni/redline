## What to build
A visitor who takes the landing page's action tries **one** document without an
account. The landing page already links to `/try`; build what is on the other end.

They get the plain-English summary and the severity-ranked flags and gaps, with
every flag's source sentence — or the **clean read** when nothing clears the
threshold. `analyzeDocument(text, [])` runs with **no red lines**.

Counter-offers, the question box, red lines and the library **need an account**.
The result says plainly what an account adds, without nagging.

**Nothing is stored.** The text stays in the browser tab. It is sent with the
analysis request and verified inside that request, but **never written to the
database**. Make this structurally true: the anonymous route must not have a
write path to the document store at all.

### The limits — decided for you, use these exact numbers
The ticket left these open. The build owner is away, so they were decided by the
orchestrator and you should implement them as given:

- **Per-IP daily limit: 3 anonymous analyses per IP per calendar day (UTC).**
- **Maximum document length: 50,000 characters of extracted text.**

Reasoning, which you should not re-derive: a freelancer's client agreement runs
roughly 1,000–4,000 words, so 50,000 characters clears a long one with room to
spare while capping what a single anonymous request can cost. Three tries a day
lets a visitor retry a failed parse and still try a second document before
signing up, while bounding daily spend per IP in a product with no payments.

Both are enforced **server-side with Supabase, before any model call** — no new
service, no new dependency, no CAPTCHA or third-party bot check (explicitly out
of scope). A refusal explains itself plainly; it must not read as an accusation.

Signed-in readers are **not** subject to the anonymous limit.

Write the rate-limit table and its policies as a migration under
`supabase/migrations/`. Remember the app must still start with the Supabase env
vars absent — decide and record what the limiter does when it cannot reach
Supabase, and make that choice deliberate rather than incidental.

## Tests
- An anonymous analysis writes **no document text and no analysis result** to the
  database. Assert on the stubbed Supabase client seeing no write.
- A request over the per-IP daily limit is refused with a plain explanation,
  **before any model call** — assert the model stub was never called.
- A document over the maximum length is refused with a plain explanation,
  **before any model call**.
- Signed-in readers are not subject to the limit.
- Every flag in an anonymous result passes the verbatim source-sentence check
  against the text sent in that request.
- The clean read is reachable anonymously (use the clean fixture).
